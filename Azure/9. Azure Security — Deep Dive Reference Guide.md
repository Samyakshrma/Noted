## 1. Microsoft Defender for Cloud

Defender for Cloud is Azure's combined **CSPM** (Cloud Security Posture Management — "is this configured safely?") and **CWPP** (Cloud Workload Protection Platform — "is this actively under attack?") service. It continuously assesses your resources and — where you enable the paid Defender plans — adds real-time threat detection per resource type (Defender for Servers, Storage, SQL, Containers, Key Vault, App Service, DNS, and more).

### 1.1 Secure Score

A single aggregated **percentage** representing your overall security posture, calculated from the ratio of completed vs. total recommendations, **weighted by the potential impact** of each one (an MFA recommendation affecting your whole tenant weighs more than a diagnostic-logging recommendation on one storage account).

- Recommendations are grouped into **security controls** (e.g., "Enable MFA," "Secure management ports," "Encrypt data at rest") — each control contributes a portion of the total possible score.
- The point of Secure Score isn't the number itself — it's using it as a **trend line**: is posture improving release over release, team over team, subscription over subscription? It's also a common way to benchmark different business units or track the ROI of a security initiative to leadership in one metric.

### 1.2 Recommendations

Individual, **actionable** findings — "Enable MFA for these accounts," "This storage account allows public blob access," "This VM is missing a critical OS patch," "This SQL server has no auditing enabled."

- Generated by checking your environment against the **Microsoft Cloud Security Benchmark** (and any other compliance standards you've opted into — see Section 5.2), which under the hood is implemented as built-in **Azure Policy** initiatives.
- Each recommendation carries a **severity** (High/Medium/Low) and, where possible, a **"Fix"** button that remediates it automatically or via a Logic App workflow, rather than making you hunt down the exact setting yourself.

### 1.3 Vulnerability Assessment

Scans your actual **workloads**, not just their configuration, for known weaknesses:

- **VMs** — an integrated scanner (Microsoft Defender Vulnerability Management) inspects the OS and installed software against known CVEs.
- **Container images** — registries (like ACR) are scanned both **pre-deployment** (block a vulnerable image from ever shipping) and **at runtime** (catch drift or newly-disclosed CVEs in images already running).
- **SQL** — scans for risky configurations, excessive permissions, and known vulnerabilities specific to database engines.

Findings from vulnerability assessment feed straight back into both **Recommendations** and **Secure Score** — it's not a separate silo, it's an input into the same posture-scoring system.

## 2. Key Vault

Key Vault is Azure's centralized service for storing and controlling access to **secrets, keys, and certificates**, backed by **HSMs (Hardware Security Modules)** at the higher tiers — meaning the cryptographic material can be generated and used _inside_ tamper-resistant hardware and never exposed in plaintext, even to Microsoft.

### 2.1 Secrets

Small, arbitrary pieces of sensitive data — connection strings, passwords, API keys, tokens. Every update creates a new **version** automatically, so you retain history without building that yourself. Access is controlled either through legacy **Key Vault access policies** or the modern, recommended **Azure RBAC for Key Vault data plane** — the same "control-plane vs. data-plane role" distinction you saw with Storage: managing the vault resource itself is different from being allowed to read what's inside it.

### 2.2 Keys

Cryptographic keys (RSA or EC) used for **encrypt/decrypt**, **sign/verify**, and **wrap/unwrap** operations — the actual cryptography that other services rely on.

- **Software-protected** keys vs. **HSM-protected** keys (Premium tier, or a dedicated **Managed HSM**) — with HSM-protected keys, the private key material genuinely never leaves the HSM boundary; every crypto operation happens _inside_ the hardware and only the result comes back out.
- This is the mechanism behind **Customer-Managed Keys (CMK)** — see Section 3.3 — where a key stored here is used to encrypt another Azure service's data at rest.

### 2.3 Certificates

Manages X.509 certificates for TLS/SSL. Under the hood, a Key Vault "certificate" is really a combination of a **secret** (the certificate plus its private key) and a **key** (the private key exposed for crypto operations) — bundled and exposed to you as one unified certificate object so you don't have to think about the seam.

- You can generate self-signed certs, import existing ones, or integrate with **partnered Certificate Authorities** (DigiCert, GlobalSign) for automated issuance.
- Services like **App Service**, **Application Gateway**, and **Front Door** can reference a certificate directly from Key Vault, so the TLS endpoint always uses the current version without manual redeployment.

### 2.4 Rotation

- **Keys** support **automatic rotation policies** — define a rotation period and a notification threshold, and Key Vault generates a new key version ahead of expiry on its own.
- **Certificates** tied to a partnered CA can similarly **auto-renew** before expiration.
- **Secrets** are the odd one out — Key Vault can't rotate a database password _at the source_ for you, because it doesn't control that external system. The standard pattern is: Key Vault emits an **Event Grid** notification as a secret nears expiry → that triggers a **Function or Logic App** → which rotates the actual credential at the source system → and writes the new value back as a new secret version.
- **Why this matters:** rotation limits the blast radius of any credential that leaks unnoticed — a stolen key or password becomes worthless once it naturally expires, rather than remaining a standing risk indefinitely.

## 3. Encryption

### 3.1 Encryption at Rest

Protects data while it's sitting on physical storage media. This is **on by default across virtually all Azure data services today** — Storage Service Encryption, Managed Disk encryption, SQL **Transparent Data Encryption (TDE)**, Cosmos DB encryption, and so on — typically using **AES-256**. It's not something you generally have to remember to _enable_; the more relevant decision is _whose key_ does the encrypting (see CMK vs. PMK below).

### 3.2 Encryption in Transit

Protects data as it moves across a network — TLS for HTTPS endpoints, SMB 3.0 encryption for Azure Files, encrypted protocols between services.

- Storage accounts have a **"Secure transfer required"** setting that rejects any connection not using HTTPS or encrypted SMB.
- You can also set a **minimum TLS version** on a storage account or App Service to reject legacy, weaker TLS negotiations outright.

### 3.3 CMK — Customer-Managed Keys

You generate and control the key (stored in **your own** Key Vault) that a service uses to encrypt your data at rest, instead of relying on a Microsoft-owned key.

- Gives you real control: you decide rotation cadence, you can **revoke access to the key** to instantly make the underlying data unreadable (a legitimate "crypto-shredding" technique for right-to-be-forgotten / decommissioning scenarios), and every use of the key is logged and auditable.
- Requires the consuming service to have a **Managed Identity** granted permission to call out to your Key Vault for encrypt/decrypt operations.
- Comes with real operational responsibility attached: **if you lose access to that key — accidentally delete it, let the vault get purged — your data becomes permanently unrecoverable.** CMK trades convenience for control; that trade has teeth.

### 3.4 PMK — Platform-Managed Keys

The default for most services: **Microsoft generates, stores, rotates, and secures the encryption key entirely on your behalf**, in Microsoft-owned Key Vault/HSM infrastructure you never see or touch.

- Zero operational overhead — nothing to configure, rotate, or accidentally delete.
- Zero visibility or control in return — you can't audit individual key usage or revoke access yourself.
- The right default for the large majority of workloads that don't have a specific regulatory or "must control our own keys" requirement.

||PMK (Platform-Managed)|CMK (Customer-Managed)|
|---|---|---|
|Who controls the key|Microsoft|You (via your own Key Vault)|
|Operational overhead|None|Rotation, access management, backup of the key itself|
|Revocable by you|No|Yes — instantly, by revoking key access|
|Risk if mismanaged|N/A|Data loss if the key is deleted/inaccessible|
|Typical driver|Default — no special requirement|Regulatory mandate, "crypto-shredding" need, key-usage audit requirement|

## 4. Zero Trust

Zero Trust is the **governing philosophy** underneath everything above — it's the reason CMK, MFA, JIT access, and continuous monitoring all exist together rather than as isolated features. It replaces the old "castle-and-moat" assumption (anything inside the corporate network is trusted) with: **assume compromise can originate anywhere, and verify continuously, not once.**

### 4.1 Verify Explicitly

Always authenticate and authorize based on **all available signals** — user identity, device health/compliance, location, the sensitivity of the resource being accessed, and behavioral anomalies — rather than a single username/password check at login and implicit trust after that.

- In Azure/Entra terms, this is implemented through **Conditional Access policies**: e.g., "require MFA and a compliant (Intune-managed) device to access this app, and block sign-in entirely from atypical/high-risk locations."
- MFA is the baseline explicit-verification signal, but Zero Trust treats it as one input among several, not the whole story.

### 4.2 Least Privilege

Grant the minimum access necessary, for the minimum time necessary — **Just-In-Time (JIT)** and **Just-Enough-Access (JEA)**, rather than broad, standing permissions.

- **Azure RBAC scoped tightly** — assign roles at the resource or resource-group level, not the subscription, and use the narrowest built-in role that satisfies the need (e.g., _Storage Blob Data Reader_, not _Owner_).
- **Privileged Identity Management (PIM)** — instead of a user holding a privileged role (like Global Administrator) permanently, they _request_ it, get **time-bound, approval-gated elevation**, and it automatically expires — eliminating standing admin access as an attack surface.
- **JIT VM Access** (a Defender for Cloud feature) — management ports like RDP (3389) and SSH (22) stay **closed by default** and only open for a specific requester, for a limited time window, on request — instead of sitting open to the internet permanently.

### 4.3 Assume Breach

Design as if an attacker is **already inside** — minimize blast radius and detect fast, rather than betting everything on prevention.

- **Network segmentation** — NSGs, subnetting, and **Private Endpoints** so that compromising one component doesn't grant lateral access to everything else.
- **Encrypt everything, end-to-end** — so that even a successful network interception or storage breach yields nothing useful.
- **Continuous monitoring and automated response** — this is where Assume Breach connects directly back to Section 1 (Defender for Cloud) and Section 5 below: you don't rely on a perimeter holding, you rely on detecting and containing the breach quickly once it happens.

## 5. "Security Center" — Threat Detection, Compliance, Monitoring (i.e., Defender for Cloud's operational capabilities)

### 5.1 Threat Detection

Each Defender plan (Defender for Servers, Storage, SQL, Containers, App Service, Key Vault, DNS, Resource Manager, etc.) analyzes signals specific to that resource type — process activity, network traffic, control-plane API calls — against threat intelligence and behavioral analytics to surface things like _"an unusual process just executed on this VM"_ or _"anomalous access pattern detected against this Key Vault."_

- Alerts land in a unified **Security Alerts** view, and can be forwarded to **Microsoft Sentinel** (Azure's cloud-native SIEM/SOAR) to correlate with signals from _other_ systems, not just Azure.
- **Fusion / kill-chain correlation** — Sentinel and Defender can chain multiple individually-low-confidence alerts (a failed login, then an unusual sign-in location, then a privilege escalation) into a single high-confidence **incident** representing one coherent multi-stage attack, rather than making an analyst manually connect the dots across dozens of separate alerts.

### 5.2 Compliance

The **Regulatory Compliance dashboard** continuously maps your actual resource configuration against named standards — the **Microsoft Cloud Security Benchmark** by default, plus optional ones you opt into like **PCI-DSS**, **ISO 27001**, **SOC 2**, **NIST 800-53**, or **HIPAA**.

- Every one of these standards is implemented under the hood as an **Azure Policy initiative** — your compliance percentage is _literally derived from_ policy compliance state, which is why Recommendations (Section 1.2), Secure Score (Section 1.1), and Compliance are all really different views over the same underlying policy engine.
- This gives auditors continuous, automatically-generated evidence instead of a manual point-in-time assessment every audit cycle.

### 5.3 Monitoring

Defender for Cloud doesn't scan once and stop — it **continuously re-evaluates** your environment's configuration and behavior as it changes, backed by an **Azure Monitor / Log Analytics workspace** as its data store.

- **Workflow automation** — wire specific alerts or recommendations directly to a Logic App or Function: auto-remediate a misconfigured storage account, auto-post a high-severity alert to a Teams/Slack channel, auto-open a ticket.
- This continuous stream is also the primary feed **into Microsoft Sentinel** for organizations running a full security operations center (SOC) across not just Azure but hybrid and multi-cloud environments too.

## How It All Connects

This is genuinely the point where the job changes. A junior engineer asks "does this work?" A senior engineer asks **"what happens when this is attacked, misconfigured, or leaked — and does the system still hold?"** Every section above is one layer of the same answer:

- **Zero Trust** is the _philosophy_ — verify continuously, grant minimally, assume compromise.
- **Key Vault** removes hardcoded secrets from your systems entirely, so "verify explicitly" has something real to check identities _against_ instead of a shared password anyone could have.
- **Encryption (CMK/PMK)** ensures that even if a control fails and data is exposed, it's exposed as ciphertext, not plaintext.
- **Defender for Cloud** is the feedback loop — it doesn't just check configuration once, it continuously tells you where the other three layers have gaps (Secure Score/Recommendations), whether your workloads are being actively attacked right now (Threat Detection), and whether you can prove any of this to an auditor (Compliance).

No individual layer is assumed to be unbreakable — that's the entire premise of **Assume Breach**. The senior-engineer mindset is designing systems where _any one_ of these layers can fail without the whole thing collapsing, and having the monitoring in place to know the moment it does.
